# CurrentStatus.md — статус разработки и план реализации

> Единственный источник истины по статусу проекта. Обновлять после каждой реализованной фичи или значимой промежуточной задачи. Исходное ТЗ — `doc/task.docx`, его содержание отражено ниже и повторно перечитывать не требуется.

Дата последнего обновления: **2026-11-03**.

## 1. Коротко о проекте

SPA для ГКСЭ (Беларусь): учёт плановых назначений казначейства по статьям расходов, распределение лимитов между подразделениями, ведение годового плана закупок (ГПЗ) с синхронизацией с площадкой `goszakupki.by`, реестр договоров/допсоглашений, квартальное казначейское планирование и фактическое исполнение по платёжным поручениям.

Режим работы согласован с пользователем: **пока однопользовательский (single-instance), без ролей и личных кабинетов** — это осознанно отложено (см. раздел 5). Вся бизнес-логика (лимиты, workflow статусов, многолетние резервирования) реализуется независимо от аутентификации и не блокируется её отсутствием.

## 2. Текущий статус backend

### 2.1. Модели данных — реализовано, в целом соответствует ТЗ

- **`PlanItem`** (`models/planItem.py`) — неизменяемый корень позиции ГПЗ: `num`, `is_public`, `is_active`, `created_at/updated_at`. Атомарная генерация внутреннего номера для непубликуемых позиций (`ClosedPlanSequence`, защита от race condition через `select_for_update`).
- **`PlanItemDetail`** — «подробная» версионируемая часть (title, okrb, val_amount, fund_cost/inner_cost, val_currency, procedure_months и т.д.), поле `status` использует `PlanItemStatus` — машина статусов **шире**, чем в ТЗ п.11: отдельные ветки для «изменение» и «исключение» (`DRAFT/DRAFT_ON_REVIEW/DRAFT_APPROVED/DRAFT_REJECTED`, `EXCLUSION_*`, плюс `ACTIVE/UPLOAD/ARCHIVE`) — хорошая основа под будущий workflow закупщик→финансист, но **сама логика переходов ещё не реализована** (см. 3.3).
- **`BudgetCosts`** — финансирование позиции по годам, привязка к функциональной/программной/внешней ЭКР классификации + собственный 4-уровневый внутренний классификатор (`InternalEconomicClassifier`, авто-подстановка родительских уровней раздел/подраздел/вид/статья в `save()`).
- **`PlanShare`** — распределение лимита по подразделениям; в `save()` инлайн-валидация превышения по количеству, по общей сумме, по fund_cost и по inner_cost (сравнение с уже распределённым по активным записям).
- **`Contract` / `ContractItem`** — реестр договоров, допсоглашения через self-FK `parent_contract`, свойства `days_remaining`/`is_urgent_warning`. `ContractItem` привязан к `PlanShare` — закрывает кейс ТЗ п.6 («несколько позиций плана → один договор» и наоборот).
- **`ContractQuarterlyFinance`** — плановое/фактическое квартальное казначейское исполнение договора (ТЗ п.7), с валидацией «факт ≤ сумма договора».
- **`TreasuryPayment`** — платёжные поручения, разнесение по внутренней/внешней ЭКР, привязка к договору **опциональна** (`contract` nullable) — заготовка под «свободные платёжки», но привязки к статье расходов без договора нет как отдельного явного механизма (см. 3.4).
- **Справочники** — Department (иерархия через self-FK), Supplier, Buyer, OkrbProduct, UnitOfMeasurement, ProcurementMethodDetail, FunctionalCode, ProgramCode, ExternalEconomicCode, InternalEconomicClassifier — реализованы, есть management-команды импорта (`import_okrb`, `import_suppliers`, `load_ekr`, `load_procurement_methods`, `seed_units`).

### 2.2. REST API — реализовано

Полный CRUD (`DefaultRouter`) почти по всем моделям: `plan_items`, `plan_items_details`, `budget_costs`, `contracts`, `payments`, `purchases`, `departments`, `buyers`, `suppliers`, справочники. Документация — `drf-spectacular` (`/api/schema/swagger-ui/`). Все эндпоинты сейчас `AllowAny` (аутентификация не подключена, см. 2.4).

### 2.3. Интеграция с goszakupki.by — починена (2026-11-02, см. Этап 5)

- **Pull (импорт)** — `views/get_data_from_goszakupki.py` (`get_purchases_view`, `get_purchases_items`, `get_data_gpz`) — теперь оба рабочих эндпоинта (`get_purchases_view`, `get_purchases_items`) вызывают реальный API (`GoszakupkiAPI.get_data`/`services/goszakupki_sync.py::fetch_purchase_items_from_api`), тестовый `api_data.json` и мёртвый `services/get_data_from_file.py` удалены.
- **`api/api.py` (`GoszakupkiAPI`)** — низкоуровневый клиент с логином/рефрешем токена через кэш Django; теперь умеет не только `get_data()`, но и `post_data()`/`put_data()` (для push).
- **Push (отправка изменений)** — `services/goszakupki_push.py` + `views/plan_sync.py`, переписаны строго по `doc/api.yaml` (create-item/update-item/delete-items). Не протестировано на живом портале (из этой среды нет сетевого доступа к `api.goszakupki.by`) — подробности и явно отмеченные допущения см. Этап 5.

Нужен отдельный подготовительный шаг — разбор структуры каждого релевантного листа — прежде чем писать конвертер. Подробности — Этап 1 плана ниже.

### 2.6. Docker / инфраструктура — частично (ТЗ п.10)

Один `docker-compose.yml`: активны только `db` (postgres:15) и `adminer`. Блоки `backend`, `frontend`, `nginx` **закомментированы** целиком. Двух профилей compose (backend-dev / frontend-dev), которые требует ТЗ п.10, пока нет — по факту сейчас единственный сценарий: контейнеры БД+adminer, backend и frontend запускаются локально вне Docker.

- `procurement/tests.py` — 45 автотестов (движок `ChangeRequest`, квартальные лимиты/отчёт/перераспределение, многолетнее резервирование, автопересчёт факта по платежам и сериализаторная валидация Этапа 4.1/4.3, push на goszakupki.by, калибровка лимитов по подразделениям и отчёт «Общие деньги» Этапа 9); остальная бизнес-логика (goszakupki-синхронизация, импортёр rd26) пока без тестов.
- Многолетнее резервирование лимитов (ТЗ п.5, пример с ДНК 2026/2027) — расчёта «сколько уже зарезервировано будущими годами по заключённым многолетним договорам» в коде не нашёл; при распределении лимитов следующего года это не учитывается автоматически.
- Механизм кнопок «изменить»/«исключить» у корневого пункта плана (ТЗ п.11 — должен создавать черновик-копию версии для предпросмотра последствий) — статусная машина под это заложена (`DRAFT`/`EXCLUSION` и их `_ON_REVIEW`/`_APPROVED`/`_REJECTED` варианты), но самого view/сервиса, который создаёт копию `PlanItemDetail`+`BudgetCosts`+`PlanShare` в новом статусе, нет.

## 4. План поэтапной реализации

Порядок согласован с пользователем: **Этап 1 — перенос данных из rd26.xlsx** (следующий приоритет). Остальные этапы — предварительный план, порядок можно скорректировать по ходу работы.

### Этап 1. Перенос данных из `input/rd26.xlsx` (текущий приоритет)

**1.1. Разбор структуры книги — выполнено.**

Книга — 32 листа. Лист **`реестр 26`** (1149 строк данных, 55 подписанных колонок A–BC + 3 колонки без подписи BD/BE/BF) — основной сводный реестр. Остальные 31 лист — вспомогательные: разбивки по конкретным внешним статьям ЭКР (`10.3.99`, `10.4.0`, `1.10.02.00` и т.п. — совпадают с `ExternalEconomicCode.code_api` из БД), тематические своды (`реагенты`, `ПО`, `обучение`, `мебель...`), служебные (`эк.классиф.`, `коды`, `свод лимиты`, `изменения по лимитам`). Для первого переноса нужен только `реестр 26` — остальные листы производные/рабочие представления тех же данных.

**Гранулярность строки (подтверждено пользователем):** одна строка = одна позиция плана (`num`, колонка G) **в разрезе подразделения** (колонка V) — если позицию закупают сразу для нескольких управлений, на неё несколько строк с разным `кол-во`/`сумма`, в сумме дающих `перв.сумма плана`. Договор (номер/дата/поставщик, колонки X/Y/Z) при этом **общий и повторяется** в каждой такой строке — подтверждено на примере `2026-102377498-1`: 2 строки, один и тот же № договора `3112/25-01`, но `V`=«ГУСМЭ»/«ГУСЭ» и разные суммы/кварталы. То есть строка реестра соответствует **`PlanShare`** (позиция × подразделение), а связь с договором для конкретного подразделения — это `ContractItem` (`plan_share` → `contract`).

**Важное расхождение с текущей моделью данных (решено):** квартальные суммы (`AV..BC`) различаются по строкам одного и того же договора (то есть по подразделениям) — в примере выше у «ГУСМЭ» и «ГУСЭ» разные квартальные цифры по одному договору `3112/25-01`. Модель `ContractQuarterlyFinance` сейчас привязана только к `(contract, quarter, year)`, без разреза по подразделению. **Решение пользователя: расширить модель** — добавить разрез по `ContractItem` (который уже несёт `plan_share`), чтобы кварталы считались по каждому подразделению отдельно, без потери детализации из реестра. Технически: добавить `ContractQuarterlyFinance.contract_item` (FK на `ContractItem`, nullable — для обратной совместимости с уже существующими записями без разбивки), изменить уникальный constraint на `(contract_item, quarter, year)` там, где `contract_item` заполнен.

**Колонки `BD/BE/BF` (уточнено пользователем):** это рабочие аналитические колонки самого специалиста, не первичные данные — **не переносятся буквально** при импорте. `BD` = ожидаемое исполнение до конца года, `BE` = остаток от ожидаемого (перерасход/недофинансирование по позиции), `BF` = рабочие пометки для сводки руководителю. При этом сама потребность — реальная и острая: специалист по мере разнесения платёжек к концу каждого квартала считает, при таком темпе расходования, сколько потребуется средств до конца квартала/года (эта аналитика зафиксирована как новая задача — см. Этап 4.4 ниже).

Сопоставление с моделями (проверено запросами к БД, не догадка):
- `G` (№ п/п, формат `2026-102377498-1`) → `PlanItem.num`.
- `H`/`I`/`J`/`K`/`L`/`M`/`N` (наименование, код ОКРБ, вид, кол-во, ед.изм., сумма плана) → `PlanItemDetail` (title/okrb/type/val_amount/val_unit/fund_cost+inner_cost) — брать из первой строки по `num` (общие данные позиции, не зависят от подразделения).
- `D`+`E` (напр. `173`+`1101008` → код `1101008173`) → `BudgetCosts.internal_economic_class` (лист. код 4-го уровня, подтверждено — код `1101008173` есть в `InternalEconomicClassifier`). `E` (`1101008`, уровень «статья») и `F` (`1101000`, уровень «вид») — денормализованные родительские уровни, за них уже отвечает `decoder_iec()`, отдельно маппить не нужно.
- `A`/`B`/`C` (`10`/`10`/`99`, подтверждено пользователем) → внешний код ЭКР **без первой цифры**: строка `"1 {A:02d} {B:02d} {C:02d}"` (пример: `"1 10 10 99"`), ищется в `ExternalEconomicCode.code_api` → `BudgetCosts.economic_class`.
- `R` (строка `Функ. кл. / Экон. кл. / Прог. кл. / Ведом. кл.`) — уже разобранный набор кодов для `functional_class`/`economic_class`/`program_class`/`department_code`, можно распарсить регэкспом как альтернативу/проверку A/B/C.
- `U` (Исполнитель, напр. `Лапко А.В.`) → `Buyer.shot_name` (формат совпадает точно).
- `V` (Управление) → `Department.short_name`, определяет строку `PlanShare`. **Проблема качества данных — решения от пользователя получены:**
  - Приписки вида «X УТО ГУФиТ» / «X УТО» (`ООиОЗ УТО ГУФиТ` — 269 строк, `ОООВТиВИ УТО ГУФиТ` — 55, `ООСиУН УТО ГУФиТ` — 52, `ООиОЗ УТО ` — 4) — это уточнение принадлежности, а не отдельное подразделение. При импорте отбрасывать суффикс с «УТО» и далее, брать базовый код.
  - `ОООВТиВИ` — не опечатка: пользователь уже поправил справочник `Department` напрямую в БД (id=23, было `ОООВТиВВ`, стало `ОООВТиВИ`) — сверено запросом к БД, сейчас совпадает 1:1 с реестром, отдельная логика не нужна.
  - Остальные несопоставленные коды (`УКСД`-12, `ГУСМЭ (УСХЭ/УСБЭ/УСГЭ)`-37, `УМПиОСД`-6, `ОМиОБУ`-3, `УПОиМС`-1, `УРСД`-2, `ГУФиТ (ФЭУ)`-1, пустые-3 — итого ~65 строк из 1603) — **пропускать при первом переносе** и включать в отчёт как «требует ручной проверки»; специалист поправит исходную таблицу, к вопросу вернёмся отдельно.
  - **Комбинации нескольких подразделений через запятую** (25 уникальных значений, ~40 строк, напр. «ГУКЭ, ГУСЭ, ГУСМЭ») — это НЕ разделение лимита между несколькими подразделениями. Пример пользователя: по `2026-102377498-557` лимит выделен отделу «Отдел метрологии и организации функционирования экспертного оборудования» (ОМиОФЭО), а закупка ведётся в интересах ГУКЭ/ГУСЭ/ГУСМЭ — но им лимит не выделяется и не уменьшается. При этом само название department-держателя лимита **в листе `реестр 26` не указано вообще** (проверено на примере строки 682) — эта информация в источнике отсутствует. Решение: добавить новое поле-связь (`PlanItemDetail.beneficiary_departments`, M2M на `Department`) для учёта «в чьих интересах закупка» отдельно от `PlanShare` (которая остаётся источником истины по выделенным лимитам). При переносе: комбо-значение из `V` парсится и пишется в `beneficiary_departments`, а сама строка **помечается «требует ручного назначения department-держателя лимита»** и не создаёт `PlanShare` автоматически — эти данные реестр не содержит.
- `L`/`N`/`AN` (кол-во, сумма плана для строки, сумма обязательств) → `PlanShare.shared_amount`/`shared_cost` для данного подразделения.
- `X`/`Y`/`Z`/`AA`/`AF`/`AG` (№ и дата договора, поставщик, сумма по строке, условия оплаты, плановая дата) → `Contract` (общий для всех строк-подразделений одной позиции — создавать/переиспользовать один раз на `(num, № договора)`) + `ContractItem` (`plan_share`, `contract_amount`, `contract_cost` — по строке). Поставщик — сопоставление по названию со справочником `Supplier`; если не найден — создаётся новая запись **без УНП** (`unp` пустой/временный, донаполнение вручную специалистом позже — решение пользователя).
- `AB`/`AE` (доп.соглашение/«Договор») → различение договор/допсоглашение → `Contract.parent_contract`.
- `AC`/`AH` → `Contract.is_urgent_warning`/`days_remaining` — не переносить, это вычисляемые свойства.
- `AD` → `Contract.is_registered_in_treasury`.
- `AJ` → decode-текст внутреннего кода ЭКР (совпадает с `name` в `InternalEconomicClassifier`) — контрольное поле, не отдельно переносимое.
- `AM` → `Contract.procurement_method_detail` (справочник `ProcurementMethodDetail`).
- `AV/AX/AZ/BB` («N квартал финансирование», уточнено пользователем) = **фактически оплаченная** сумма за квартал → `ContractQuarterlyFinance.actual_cost` (по `ContractItem`, см. выше).
- `AW/AY/BA/BC` («N квартал подлежит к оплате», уточнено пользователем) = динамический остаток к оплате в квартале (уменьшается по мере разнесения платёжек, не статичный исходный план). Исходный план на квартал реконструируется как `финансирование + подлежит к оплате` (сумма на момент снятия среза) → `ContractQuarterlyFinance.planned_cost`.
- `BD` («ожидаемое до конца года») / `BE` («остаток от ожидаемого») / `BF..BI` (без подписи) — рабочие аналитические колонки специалиста, **не переносятся буквально** при импорте; сама потребность (прогноз исполнения) зафиксирована как отдельная задача — Этап 4.4.

**1.2. Маппинг колонок — выполнено.** Подразделения (`V`) тоже решены: суффиксы «X УТО ГУФиТ» отбрасываются (база — X), `ОООВТиВИ` сверено с БД (пользователь уже поправил справочник, совпадает 1:1), комбинации через запятую → `beneficiary_departments` + пропуск `PlanShare` (держатель лимита реестром не сообщается), прочие несопоставленные коды (~65 строк) — пропускаются с пометкой в отчёте, к ним вернёмся отдельно, когда специалист поправит исходную таблицу.

**Реализовано и применено к БД** (миграции накатаны):
1. `ContractQuarterlyFinance.contract_item` (nullable FK на `ContractItem`) + новые constraints — разрез квартального плана/факта по подразделению.
2. `PlanItemDetail.beneficiary_departments` (M2M на `Department`) — для строк-комбинаций.

### Этап 2. Универсальный движок одобрения изменений — выполнено (2026-11-02)

Решение пользователя: проектировать сразу как общий движок, обслуживающий несколько сценариев одним механизмом статусов, а не отдельными для каждого случая. Реализовано:

**Новая модель `ChangeRequest`** (`models/changeRequest.py`) — заявка на изменение, с собственным простым статусом `ChangeRequestStatus` (`DRAFT`/`ON_REVIEW`/`APPROVED`/`REJECTED`, новый enum в `core/choices.py` — не переиспользует раздутый `PlanItemStatus`, он остаётся статусом версионирования дочерних снимков) и `ChangeRequestKind` (`PLAN_ITEM_CHANGE`/`PLAN_ITEM_EXCLUSION`/зарезервировано `BUDGET_LIMIT_CORRECTION` для Этапа 3.4 — сервис на нём осознанно выбрасывает `NotImplementedError`). `plan_item` — nullable (для будущего сценария (б), где цель может не сводиться к одной позиции). `PlanItemDetail`/`BudgetCosts`/`PlanShare` получили nullable FK `change_request` (миграция `0046`) — связывает дочерний черновик-снимок с заявкой.

**Сервисный слой** `procurement/services/change_requests.py`:
- `create_change_request(plan_item, kind, reason='')` — для `PLAN_ITEM_CHANGE` клонирует ВСЕ активные `PlanItemDetail`+`BudgetCosts`(все года, решение пользователя)+`PlanShare` в статус `DRAFT`, привязывая к заявке; для `PLAN_ITEM_EXCLUSION` (решение пользователя: без редактируемого черновика полей) — создаёт заявку сразу в `ON_REVIEW` с обязательным `reason`, без копирования дочерних записей. Не больше одной открытой (DRAFT/ON_REVIEW) заявки на одну позицию одновременно (решение пользователя) — проверяется перед созданием.
- `submit()` — `DRAFT` → `ON_REVIEW`, дочерние снимки → `PlanItemStatus.DRAFT_ON_REVIEW`.
- `approve()` — для изменения: архивирует старые ACTIVE-снимки, активирует черновик (поштучно через `.save()`, не bulk `.update()` — чтобы бизнес-валидация `PlanShare` реально проверила финальное состояние), **перепривязывает существующие `ContractItem` со старого `PlanShare` на новый** (совпадение по подразделению + логической идентичности строки бюджета год+budget_code+economic_code — тот же приём, что в Проходе 10) — без этого уже заключённые договоры "терялись" бы для отчётности после архивации старой строки. Для исключения — архивирует всё и переводит `PlanItem.is_active=False`.
- `reject(reason)` — черновик помечается `*_REJECTED` (не удаляется, это история), причина фиксируется.
- `compute_forecast()` — «прогноз последствий» (2.3): для изменения сравнивает новую сумму черновика с уже принятыми обязательствами (`ContractItem.contract_cost`) по статье и по подразделению; для исключения показывает, что уже принято/оплачено и «осиротеет» при архивации.

**Побочный фикс, найденный при проектировании:** `PlanShare.save()` валидировал бизнес-ограничения (превышение лимита) безусловно — при клонировании ACTIVE-строки в DRAFT (старая ещё жива) это ложно давало "превышение", так как новая черновая копия добавлялась к сумме ещё не заархивированного оригинала. Все 4 проверки в `PlanShare.save()` теперь выполняются только при `self.status == PlanItemStatus.ACTIVE` — черновики не обязаны соответствовать лимиту до момента, когда реально становятся действующими.

**API**: `ChangeRequestViewSet` (`views/changeRequest.py`) — `POST /api/change_requests/` (создание), `POST .../{id}/submit|approve|reject/`, `GET .../{id}/forecast/`. `AllowAny`, как и весь остальной API (авторизации нет, осознанно отложено).

**Проверено:** 5 автотестов (`procurement/tests.py`, были пустым шаблоном) — полный цикл изменения (создание→правка черновика→прогноз обнаруживает перерасход→отправка→одобрение→перепривязка договора на новый `PlanShare`→ровно один ACTIVE-снимок каждого типа), отклонение (старое не тронуто, черновик помечен REJECTED), запрет второй параллельной заявки, обязательность причины и отсутствие черновика полей у исключения, `NotImplementedError` на зарезервированном виде. Все зелёные. Дополнительно — `manage.py check`, генерация схемы `drf-spectacular` (новых ошибок не добавилось), живой HTTP-запрос к `/api/change_requests/` (200).

### Этап 6. Docker-compose (ТЗ п.10) — выполнено (2026-10-29)

Реализовано через Compose **profiles** (один `docker-compose.yml`, запуск явный — без `--profile` ничего не поднимается):

- `docker compose --profile prod up -d --build` — полный стек: `db` + `adminer` + `backend` (gunicorn) + `frontend` (собранная статика) + `nginx` (единая точка входа на 80). По решению пользователя `adminer` оставлен доступным и в проде (осознанный выбор, не блокирующая рекомендация).
- `docker compose --profile backend-dev up -d --build` — `db` + `adminer` + `frontend` (чужая разработка, не редактируется — собирается и разворачивается как есть на `localhost:8090`). Backend запускается локально (IDE/venv) с подключением к `localhost:5460`.
- `docker compose --profile frontend-dev up -d --build` — `db` + `adminer` + `backend` (контейнер, `localhost:8000`). Frontend запускается локально (`npm run dev`).

Технические решения:
- **Frontend теперь собирается в production-режиме** (`docker/frontend/Dockerfile`, multi-stage: `node:22-alpine` → `npm run build` → `nginx:alpine` отдаёт `dist/`). Файл лежит **вне `frontend/`** (запрет на запись туда не нарушен — Dockerfile только читает файлы внутри одноразового build-контейнера, явный список COPY вместо `COPY . .` — чтобы не затащить в образ `node_modules`/`dist` разработчика поверх уже установленных внутри контейнера, Windows/Linux native-бинарники иначе ломаются). Контекст сборки — корень репозитория, добавлен `.dockerignore` (тоже вне `frontend/`) для скорости сборки.
- `nginx/nginx.conf` (edge) обновлён: `upstream frontend` теперь `frontend:80` (свой nginx с готовой статикой) вместо `frontend:5173` (Vite dev-сервер).
- `VITE_API_URL` (base URL API) зашивается в сборку фронтенда на этапе build (Vite inlines `import.meta.env.*`): по умолчанию `/api/` (относительный путь, т.к. в prod фронтенд и API отдаёт один nginx с одного домена); для `backend-dev` (без edge-nginx) переопределяется через `FRONTEND_API_URL` в `.env`.
- **Обнаружено и проверено отдельно (не блокирует Этап 6, вне моей зоны):** реальная prod-сборка фронтенда (`npm run build` = `tsc -b && vite build`) **падает на текущих TypeScript-ошибках в коде `frontend/`** — не связано с Docker-конфигом (`plans-items.page.tsx`, `use-department-form.ts`, `crud-service.ts` — отсутствует `axios` в зависимостях, `calendar.tsx`). По решению пользователя `npm run build` в Dockerfile оставлен как есть (без обхода тайпчека) — сборка заработает, когда фронтенд-разработчик исправит эти ошибки у себя.
- Конфигурация проверена: `docker compose --profile <X> config` для всех трёх профилей резолвится корректно (правильный набор сервисов, build-args, env, depends_on, volumes); `docker compose --profile prod build frontend` реально собирался (упал только на вышеупомянутом тайпчеке — т.е. Docker-механика пройдена до конца, `npm ci` + копирование + сборка работают).

### Этап 9. Отчётность — backend первого отчёта + механизм калибровки лимитов выполнены (2026-11-03)

Пользователь обозначил, что отчётов будет **много** — либо отдельные страницы, либо одна страница с пунктами меню (один пункт = один вид отчёта). Первый отчёт — **«Общие деньги»**.

**9.1. Найдена и закрыта архитектурная развилка — «доведённые лимиты по подразделениям».** При проектировании колонки «доведено лимитов» выяснилось, что такой сущности в системе не было вовсе: `PlanShare` считает деньги, уже привязанные к КОНКРЕТНЫМ позициям плана (= «внесено в ГПЗ», не что-то большее); `ArticleQuarterlyAllocation` (Этап 3.4) — агрегат Минфина по статье целиком, без разбивки по подразделениям. Проверено на реальном `input/rd26.xlsx` (лист «свод лимиты») — там тоже только ОДНО число «лимит» на статью, без разбивки; лист «держатель лимита» — справочник «статья→ОДНО подразделение», не суммы.

Пользователь описал реальный процесс (2026-11-03): Минфин доводит укрупнённые суммы по статьям → финансист делит статью на **подстатьи** (наш внутренний классификатор) → каждая подстатья делится между **держателями лимита** (подразделениями). При корректировке Минфином статьи в течение года — нужно пересчитать/докалибровать подстатьи и держателей, не набирая с нуля; **история корректировок обязательна**.

**Реализовано:**
- Новая модель **`DepartmentArticleLimit`** (`models/departmentArticleLimit.py`) — та же версионируемая схема (status/change_request), что у `BudgetQuarterlyLimit`. Два уровня одной модели: `department=NULL` — сумма на подстатью целиком; `department` заполнен — доля конкретного держателя. Та же схема full-snapshot архивации при одобрении, что у `ArticleQuarterlyAllocation`.
- Новый `ChangeRequestKind.DEPARTMENT_LIMIT_CALIBRATION` в общем движке `ChangeRequest` (Этап 2) — `create_department_limit_calibration()` клонирует текущие ACTIVE строки в черновик (не с нуля при повторной калибровке); `submit`/`reject`/`approve` подключены в общий диспетчер; `compute_forecast()` → `_forecast_department_limits()` считает две сверки.
- **Важное уточнение формулы (найдено при тестировании на числовом примере пользователя):** первая версия сверки требовала ТОЧНОГО совпадения (сумма подстатей == сумма статьи) — но тогда «нераспределённые лимиты» в отчёте были бы ВСЕГДА равны нулю после любой одобренной калибровки, что прямо противоречит собственному примеру пользователя (план 500000 − резерв 150000 − доведено 250000 = нераспределено **100000**, положительный остаток — нормальное состояние). **Исправлено**: блокируется только ПЕРЕРАСХОД (`approve()` отказывает, если сумма подстатей > доступно по статье ИЛИ сумма держателей подстатьи > сумма самой подстатьи) — недораспределение разрешено и просто отражается остатком. Сверка №1 также учитывает многолетнее резервирование прошлых лет (`compute_reserved_amount_by_article()`, новая статья-level версия `multi_year_reservation.py`) — сравнивается не с планом целиком, а с планом МИНУС резерв, точно как в примере пользователя.
- `services/department_limits.py::compute_available_department_limit()` — остаток доведённого держателю лимита за вычетом уже зарезервированного через `PlanShare` (та же идея, что в многолетнем резервировании, но для текущего года: «в BudgetCosts также находятся лимиты-части подразделений... суммы резервируются», пользователь 2026-11-03).
- CRUD `DepartmentArticleLimitViewSet` (`/api/department_article_limits/`) — специалист правит строки черновика обычным REST; новая custom-action `ChangeRequestViewSet.calibrate_department_limits` (`POST /api/change_requests/calibrate_department_limits/`) создаёт заявку калибровки.

**9.2. Отчёт «Общие деньги»** (`services/general_money_report.py`, `GET /api/reports/general_money/?year=`) — одна строка на статью (functional_class+economic_class), org-wide, без разбивки по подразделениям (разбивка по держателям — уже существующий `/api/reports/budget_execution/`, Этап 4.4). Колонки и формулы — как сформулировал пользователь 2026-11-03 (плюс один столбец, добавленный тем же сообщением):
- `planned_annual` — план Минфина за год (сумма кварталов `ArticleQuarterlyAllocation`).
- `prior_years_obligations` — обязательства прошлых лет (многолетние договоры, `compute_reserved_amount_by_article`).
- `allocated_limit` — доведённые лимиты (сумма подстатей `DepartmentArticleLimit`, department=NULL).
- `unassigned_limit` — нераспределённые лимиты: `planned_annual − prior_years_obligations − allocated_limit`.
- `entered_into_plan` — внесено в ГПЗ (публ.+непубл.): сумма `BudgetCosts.cost`.
- `committed_obligations` — принято обязательств (текущего года): `ContractItem.contract_cost`, где и строка договора, и её бюджетная строка — этого года (не пересекается с `prior_years_obligations`).
- `paid_actual` — фактическая оплата: нетто `TreasuryPayment` (с учётом `KindOfPayment.is_refund`) — см. ниже про сопоставление.
- `unallocated_limit` — остаток незапланированных средств: `allocated_limit − entered_into_plan`.
- `remainder_unobligated` — остаток от принятых обязательств: `planned_annual − committed_obligations − prior_years_obligations`.
- `remainder_with_actual` — остаток с учётом фактических расходов (добавлено пользователем): `planned_annual − paid_actual`.

**Found & fixed попутно:**
1. Сопоставление платежей со статьёй — большинство `TreasuryPayment` (1599 из 1616, все привязанные к договору) НЕ имеют `economic_class`/`functional_class` заполненными напрямую (проверено на реальных данных) — матчинг идёт через `internal_economic_class` (заполнен у 1609/1616) + мост через `BudgetCosts` той же статьи/года. Но 3 из 17 «свободных» платёжек имеют `economic_class` заполненным напрямую, БЕЗ `internal_economic_class` — для них добавлено прямое сопоставление через `Q(...) | Q(...)`, иначе эти 3 платежа выпадали бы из отчёта.
2. `ArticleQuarterlyAllocation.objects.values('functional_class_id','economic_class_id').distinct()` без явного `.order_by()` возвращал по строке на КАЖДЫЙ квартал вместо одной строки на статью — дефолтная сортировка модели (`['year','quarter']`) просачивается в `DISTINCT`, когда `quarter` не входит в `values()` (известная особенность Django ORM). Исправлено явным `.order_by()` перед `.values().distinct()`.

**Проверено:** `manage.py check`, **45/45 тестов** (12 новых: калибровка — создание/недораспределение-разрешено/перерасход-блокирует/сверка с резервом/полная замена снимка; `compute_available_department_limit`; отчёт — числовой пример пользователя целиком, плюс сопоставление «свободного» платежа без `internal_economic_class`).
